# AI_RULES — Agent FX Bot (IBKR + Supabase)

Этот файл — обязательные правила для любого AI-разработчика (Codex/Cursor/LLM), работающего в репозитории.
Нарушение любого пункта = работа считается неприёмлемой.

---

## 1) Источник истины

1) Следовать `docs/spec_v1.md` как единственному функциональному ТЗ для v1.
2) Если встречается конфликт между предложением AI и Spec — **Spec важнее**.
3) Если чего-то нет в Spec — AI **не должен додумывать**. Нужно либо:
   - оформить как вопрос/блокер, либо
   - добавить в Spec короткое уточнение (если прямо запрошено).

---

## 2) Жёсткие запреты (Hard constraints)

### 2.1 LLM и числа
- LLM **не считает**: цены, SL/TP, pip, лоты, маржу, leverage, риск, размер позиции, PnL, комиссии.
- LLM может возвращать только: `trade_allowed`, `risk_modifier`, `flags`, `comment`.

### 2.2 Контракты данных
- Внутри доменной логики (signals/agents/decision/risk/execution/recon/pm) — **только Pydantic-модели**.
- Никаких “сырых dict/JSON” между слоями.
- Исключение: **на границах** (storage/network/broker adapters) допускается dict/json **только для сериализации**.

### 2.3 База данных и миграции
- Нельзя пересоздавать БД, таблицы, RLS-политики, роли, auth, структуру схемы.
- Нельзя делать UPDATE/DELETE для append-only таблиц (кроме разрешённых mutable-таблиц).
- Единственные допустимые изменения схемы в рамках текущих задач: **миграции строго по запросу владельца** (пример: триггеры deny update/delete для append-only).

### 2.4 Execution безопасность
- Нельзя писать/менять код исполнения так, чтобы допустить “позиция без SL”.
- Любая ошибка/неопределённость → fail-safe (no new entries; при SL fail — close).

### 2.5 Scale-in (v1)
- Scale-in / add-to-position **запрещён** в v1.
- Любая попытка доливки должна блокироваться и логироваться.

### 2.6 “Метод тыка”
- Запрещено “вслепую подгонять” код под запуск.
- Запрещено менять зависимости/окружение без явного запроса владельца.
- Если что-то не запускается в среде — фиксируется как отдельная задача, не мешающая текущей цели.

## 3) Архитектурные принципы (обязательные)

1) **Fail-safe по умолчанию**:
   - ошибка агента → `trade_allowed=false`
   - ошибка SL → немедленное закрытие позиции
2) **Idempotency**:
   - каждый intent/decision имеет `decision_id`
   - повтор одного `decision_id` не приводит к повторному входу/ордеру
3) **Append-only логи**:
   - snapshots/signals/agent_reports/decisions/execution_reports/orders/fills/risk_events — неизменяемые записи
   - mutable: только `positions`, `bot_settings` (и только по правилам)
4) **UI не трогает runtime**:
   - UI управляет ботом только через `bot_settings`
5) **Изоляция LLM**:
   - агенты не являются SPOF, таймауты и fallback обязательны

## 4) Правила задач и формата работы (как писать изменения)

### 4.1 Перед кодом: контракты и документы
Для новых подсистем сначала:
- краткий контракт (Pydantic модели / протоколы)
- 1–2 страницы документа (или раздел в existing docs)
Потом — код.

### 4.2 Изменения должны быть минимальными
- Не рефакторить “ради красоты”.
- Не перемещать файлы/директории без запроса владельца.
- Не менять существующие контракты без явной причины и миграционного плана.

### 4.3 Обязательные поля трассировки
Везде, где уместно:
- `decision_id`
- `symbol`
- `ts` (UTC)
- correlation ids для исполнения (order_id/fill_id) — как факты из брокера/OMS, не вычисления

## 5) Качество и тесты (минимум)

Каждая задача должна сопровождаться:
- минимальными тестами валидаторов (Pydantic), idempotency, risk-gates (если затронуто)
- чётким списком изменённых файлов
- кратким “Definition of Done” (что именно стало возможно/зафиксировано)

---

## 6) Acceptance checklist (самопроверка AI)

Перед тем как предложить diff/patch, AI обязан проверить:

- [ ] Не добавлял вычисления чисел в LLM (цены/SL/TP/лоты/маржа)
- [ ] Внутри доменной логики использовал только Pydantic (нет raw dict между слоями)
- [ ] Не менял БД/RLS/таблицы, кроме явно разрешённой миграции
- [ ] Не внедрял scale-in (v1 запрещён)
- [ ] Не нарушил fail-safe (нет сценария “позиция без SL”)
- [ ] Сохранил idempotency по `decision_id`
- [ ] Не “чинит запуск” и зависимости без запроса владельца
- [ ] Добавил/обновил docs согласно Spec

---

## 7) Если что-то неясно
AI должен задать **ровно один** уточняющий вопрос, который снижает неопределённость.
Если вопрос не критичен — оформить как TODO/блокер в docs, без реализации “по догадке”.
